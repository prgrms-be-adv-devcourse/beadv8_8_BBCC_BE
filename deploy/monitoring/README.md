# 모니터링 운영 안내

[Grafana](https://grafana.kidly.kro.kr)의 Kidly 폴더에서 지표와 로그를 보고, 장애 알림은 Slack으로 받습니다.
**dev·prod 동시 운영이 목표**이며, 점검할 때 필요한 환경만 중지합니다.

## 평소 확인할 화면

| 화면 | 확인할 것 |
| --- | --- |
| Kidly 서비스 오류 | 환경별 운영 상태, 서비스 수집 상태, 5xx·요청량 |
| Kidly 로그 | 서비스별 ERROR·느린 요청, 같은 요청의 로그 |
| 서버 | 서버별 메모리·디스크·CPU, 컨테이너 자원 사용량 |

먼저 환경과 시간을 고릅니다. 수집 정상은 지표를 받는다는 뜻이며 업무 정상까지 보장하지는 않습니다.
수집기·전송 상세는 서비스 오류 대시보드의 접힌 행에서 확인합니다.

## 환경 중지·재개

1. GitHub Actions → **environment-operation** → **Run workflow**를 엽니다.
2. 환경(`dev`/`prod`)과 동작(`stop`/`resume`)을 선택합니다. **prod는 main 브랜치**에서 실행하며, Environment 승인 정책을 따릅니다.
3. 실행 완료와 Grafana의 운영·수집 상태를 확인한 뒤 다음 작업을 실행합니다.

| 동작 | 결과 |
| --- | --- |
| stop | 선택 환경의 앱·DB·Kafka를 중지하고 앱 장애 알림 대상에서 제외 |
| resume | 기존 이미지로 기동하고 수집·앱 장애 감시 재개 |

DB·볼륨·과거 지표·로그는 유지하며, 다른 환경은 중지하지 않습니다.
최초 앱 배포가 끝난 환경에서 사용합니다. 중지한 환경은 자동 배포로 다시 켜지지 않습니다.
**서버 파일을 직접 지우거나 수정해서 감시를 해제하지 않습니다.**

## 실패하거나 알림이 오면

- **중지·재개 실패:** Actions의 실패 단계를 확인합니다. 중지 확인에 실패하면 컨테이너를 내리지 않습니다. 재개 도중 실패하면 감시는 유지하므로 원인을 해결하고 `resume`을 다시 실행합니다.
- **앱 다운·5xx·ERROR:** 알림의 환경·서비스를 확인하고 같은 시간의 서비스 오류 화면과 로그를 봅니다. Gateway와 하위 서비스의 요청 수는 합산하지 않습니다.
- **데이터 끊김:** 서비스 하나만 끊겼는지, 앱 수집기 전체가 끊겼는지 먼저 구분합니다. 의도적 중지는 회색 상태로 표시합니다.
- **전송·저장 실패:** 대시보드의 수집기·전송 상세와 Alloy 로그를 확인합니다. 수신 데이터가 없다고 정상으로 판단하지 않습니다.

앱 다운은 5분, 서비스별 5xx는 최근 5분 오류 비율 5% 초과·추정 5건 이상이 2분 지속할 때 알립니다.
ERROR는 최근 5분 추정 건수 4.5 초과가 2분 지속할 때 알립니다. 수집 누락은 3분 부재 후 2분 대기하며, 재개 초기 5분은 유예합니다.
이 기준은 초기값이며 실제 트래픽을 보고 조정합니다.

## 설정 변경·배포

대시보드·알림·수집 설정은 **저장소 파일**을 수정해 PR로 반영합니다. Grafana 화면 수정은 다음 배포에 유지되지 않습니다.
모니터링 설정은 develop 머지 후 `monitoring-deploy`로 배포하며, 수동 재배포도 같은 워크플로를 사용합니다.
비밀값은 GitHub Secrets로 관리하고, Grafana 관리자 비밀번호도 화면이 아닌 Secret에서 변경합니다.

## 알아둘 제약

- 모니터링 서버(t3.medium) 자체가 꺼지면 이 구성으로는 알릴 수 없습니다. 외부 감시는 #775 범위입니다.
- 외부 EC2 자동 정지는 운영 중지 기록을 남기지 않습니다. 자동 정지 정책과 운영 절차를 별도로 연결해야 합니다.
- 두 환경을 함께 실행할 메모리 여유와 서비스별 상한은 #773에서 실측합니다.
