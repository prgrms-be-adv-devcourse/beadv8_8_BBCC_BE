# 요청 로그 최소 수집 정책

사용자 승인 후 공통 필터와 분리된 회원 서비스의 같은 필터에 적용했습니다. 요청 본문을 버퍼링하지 않으며 정규화 경로·상태·소요시간·traceId만 남깁니다.
앱 설정·보관 기간·기존 로그 데이터는 변경하지 않습니다. 도메인이 별도로 남기는 로그의 개인정보까지 이 필터가 제거하는 것은 아닙니다.

## 기본 요청 로그

| 기본 수집 | 기본 제외 |
| --- | --- |
| 시각, 서비스, 환경, method, 정규화 route, status, duration, traceId | 요청·응답 본문, 전체 헤더, query string, IP·회원 ID·사용자 식별값 |

정규화 route가 없는 요청은 실제 URL 전체 대신 고정 `UNKNOWN`으로 기록합니다. 주문·회원 ID가 들어간 경로를 라벨로 쓰지 않습니다.
traceId는 한 요청을 찾는 구조화 메타데이터로 유지하고 Prometheus/Loki 인덱스 라벨에는 추가하지 않습니다.
토큰·웹훅·결제 키·연락처·주소·원시 SQL·이벤트 payload를 알림 메시지에 넣지 않습니다.

## 본문이 꼭 필요한 조사

1. 담당자·문제·필요 필드·대상 환경·서비스·최대 시간·종료 시각을 먼저 정합니다.
2. 운영 기본은 비활성으로 둡니다. dev의 합성 데이터로 재현을 우선합니다.
3. 본문 전체가 아니라 허용한 필드만 수집합니다. 인증·결제·아동 관련 민감 데이터는 예외 수집 대상에서도 제외합니다.
4. 접근자·저장 위치·보관 기간을 별도로 승인합니다. 현재 Loki 보관 기간을 임의로 단축하거나 데이터를 삭제하지 않습니다.
5. 종료 후 옵션 원복·수집 중단을 확인합니다. MCP·AI 반출은 추가 승인 없이 하지 않습니다.

## ERROR 호출

- 개별 ERROR 한 줄마다 호출하지 않습니다. 현재 서비스별 반복 오류 조건과 5xx·다운·처리 정체를 함께 봅니다.
- 업무 실패를 기술 ERROR로 모두 취급하지 않고, 필요한 상태·건수는 도메인 담당이 낮은 카디널리티 업무 지표로 제공합니다.
- 로그 내용은 호출 메시지에 넣지 않습니다. 환경·서비스·시간·대시보드 링크로 조사합니다.

## 검증

- `common` 변경과 dev 검증은 사용자 승인을 받았습니다.
- 합성 요청으로 기본 로그의 본문·헤더·식별값 제외, 정규화 경로·상태·소요시간·traceId 보존을 확인합니다.
- 로그 원문을 PR에 붙이지 않습니다. 같은 합성 요청의 줄 크기와 traceId 조사 성공 여부를 비교하며, 이 결과를 전체 트래픽 수집량 감소율로 해석하지 않습니다.
- 기존 ERROR/5xx 로그 링크가 유지되는지 dev에서 확인합니다. 실제 개인정보를 시험 데이터로 만들지 않습니다.

## dev 실증 결과 (2026-11-05 KST)

동일한 합성 POST 요청을 공통 앱과 회원 서비스의 미등록 경로에 각각 보냈습니다. 업무 데이터는 생성하지 않았으며, 응답은 변경 전후 모두 404였습니다.

| 대상 | 변경 전 한 줄 | 변경 후 한 줄 |
| --- | ---: | ---: |
| 공통 앱 | 1,224 bytes | 482 bytes |
| 회원 서비스 | 1,232 bytes | 493 bytes |

두 서비스 모두 요청·응답 본문과 헤더, 회원 식별값, IP, 식별값을 포함한 원본 경로가 제외됐습니다. traceId는 유지됐고 미등록 정적 자원 요청은 Spring 정규화 패턴 `/**`로 기록됐습니다. 다른 매핑이 없는 요청은 단위 테스트에서 `UNKNOWN`을 확인했습니다. 값은 합성 요청 한 건의 비교이며 장기 트래픽 절감률은 아닙니다.

dev 앱 11개와 DB·Kafka 모두 healthy, 기존 앱 경보 inactive를 확인했습니다. 시험 배포 뒤 develop 이미지로 원복하며 prod 앱·운영시간·보관 기간·기존 로그는 변경하지 않습니다.
