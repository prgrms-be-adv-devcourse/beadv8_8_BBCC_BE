# AI 운영 분석 메모 · 설계 단계

목적은 **실제 AI가 지표를 읽고 추론한 원인 후보·확인 순서·대응 제안**을 Grafana에 남기는 것입니다.
규칙 기반 문구를 AI 분석으로 대신하지 않습니다. 현재는 계약/검증 코드만 있으며 실제 게시 기능은 아직 없습니다.

## 바뀌는 부분 / 유지되는 부분

```text
지표 → AnalysisContext → AI 구현체 → AnalysisReport → NotePublisher → Grafana
```

| 경계 | 책임 | 교체 범위 |
| --- | --- | --- |
| AnalysisContext | 관측 시각·환경·허용된 기술 지표·누락/제약 | 지표를 읽는 방식과 AI 종류 분리 |
| AnalysisProvider | 실제 AI 호출·추론과 결과 형식 변환 | 외부 제공자 또는 로컬 모델 어댑터 |
| AnalysisReport | 관측·원인 가설·확인 순서·대응 제안·근거 ID | 모든 AI가 같은 출력 계약 사용 |
| NotePublisher | 검증된 메모 저장과 게시 | Grafana 표시와 AI 제공자 분리 |

호출 URL/모델/인증/timeout은 구현체 설정입니다. 키는 계약·결과·대시보드에 넣지 않습니다.
모든 모델이 같은 HTTP API를 쓴다고 가정하지 않습니다. 제공자마다 요청/응답 변환 어댑터를 둡니다.
Grafana는 provider/model과 관측/작성 시각·제약을 표시하며 특정 모델 응답 원문 구조를 읽지 않습니다.

## 실행 방식 두 가지

- **MCP 클라이언트 AI:** AI 앱이 MCP로 지표/문맥을 받고 추론한 뒤 공통 AnalysisReport를 제출합니다. 서버가 MCP에 AI 추론을 요청한다고 가정하지 않습니다
- **서버/로컬 모델 worker:** AnalysisProvider.analyze(context)를 구현한 어댑터가 실제 모델을 호출하고 같은 결과를 게시합니다

두 경로 모두 publish_analysis에서 같은 계약 검증을 거칩니다. 예약 실행기는 교체 가능한 별도 호출 주체이며 분석/게시 코드에 스케줄을 넣지 않습니다.
MCP는 도구 연결 규약이고 AI 모델 자체가 아닙니다. MCP 클라이언트가 추론하는 흐름과 서버가 모델 HTTP API를 부르는 흐름은 호출 주체가 다릅니다.

## 검증과 실패

- schema version·context ID·근거 ID·관측/생성 시각·크기·유한 숫자를 검증합니다
- 모르는 필드/제공자 응답 파싱은 어댑터 책임입니다. 공통 검증 뒤에만 게시합니다
- 키·로그 원문·개인 식별값은 문맥 생성 단계에서 제외합니다. 형식 검증만으로 개인정보/AI 환각을 완전히 막는다고 보장하지 않습니다
- 거절/타임아웃/틀린 결과는 실패/판단 불가로 남깁니다. 다른 유료 AI로 자동 전환하지 않습니다
- 사실·가설을 분리하고 수집 누락·운영 중지·저트래픽 제약을 보존합니다. 원인을 확정하거나 서비스를 자동 조작하지 않습니다

## 다음 검증

1. 기존 AI 클라이언트 + MCP로 실제 분석 한 번을 생성
2. 별도의 메모 게시 경로만 제한적으로 연결. 기존 Grafana MCP Viewer는 그대로 유지
3. 실제 게시·실패/오래됨 표시 검증 후 예약 실행 검토

새 유료 제공자·모델 서버·이미지·계정·게시 권한은 도입 전 범위를 확인합니다.
로컬 오픈소스 모델도 실행할 장비 자원이 필요하며, 현재 작은 앱/모니터링 서버에 임의 설치하지 않습니다.
현재 API 호출·새 자격증명·모델 설치·예약 실행 활성화는 없습니다.
