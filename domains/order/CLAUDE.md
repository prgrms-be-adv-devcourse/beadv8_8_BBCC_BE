# 주문 도메인 설계 규칙

주문 모듈(주문 · 장바구니 · 배송 · 조르기 컨텍스트) 안의 설계 규칙이다. 도메인 경계 · `shared` 계약 · Kafka 토픽/키/그룹 · 묻고 바꿀 것은 루트 `CLAUDE.md`를 따르고, 여기와 부딪히면 루트가 우선이다.

## 1. 컨텍스트 · 계층과 포트
- 이 모듈은 컨텍스트 넷이다: `boundedcontext.order`(주문 · 결제 반영 · 만료 · 구매확정 · 이력 · 재처리 · 아웃박스 · DLT · 관리자 · 상품/판매자/자녀 복사본), `boundedcontext.cart`(장바구니), `boundedcontext.delivery`(판매자별 배송 · 발송 · 배송 완료 · 판매 주문 조회), `boundedcontext.wish`(조르기, 아래). 저장은 모두 `orders` 스키마다
- `boundedcontext.wish`(조르기 = 구매 요청, #999. 승인 = 결제)는 팀이 정책을 확정하지 않아 걷어낼 수 있게 둔다: 아무 컨텍스트도 wish를 참조하지 않고(wish는 들어오는 포트가 없다), wish는 장바구니만 안다(장바구니 칸 예약 입구 `CartReservations` 호출 · 장바구니 구매 이벤트 수신. 주문 · 배송은 모른다). 표는 `wish_request` · `wish_request_line`(장바구니 칸 · 보낸 때 상품 · 옵션 · 수량) · `wish_purchase`(조르기로 산 것: 조르기 · 주문 · 칸, 주문상품과는 (주문 ID, `order_item.cart_item_id`)로 맞춘다, #1000이 쓴다). 스위치 `kidly.order.wish.enabled`(false면 빈 · API 없음, 모든 빈에 같은 조건), 정책(보내는 사람 · 메시지 길이 · 거절 · 철회 주체 · 거절 사유 목록)은 `WishPolicy` 한 곳, 호출 주체는 `app.port.WishActor`(구현은 out)
  - 모델(`WishRequest`): 종류 `type`(WISH만) · 보낸 사람 · 결제한 사람 · 거절한 사람은 주체 종류(`PrincipalType` MEMBER · CHILD) + ID, 받는 사람은 자녀 프로필(`child_id`). 상태 REQUESTED · PAID · REJECTED · CANCELLED(원인 `cancel_reason` DIRECT · CHILD_DELETED · ACCOUNT_DELETED · SYSTEM) · EXPIRED(#1008). 결제 완료 · 거절 · 철회 · 만료는 REQUESTED에서만, @Version으로 한 번만(동시에 오면 진 쪽 409)
  - 승인자: 저장하지 않고 `app.port.WishApprovers`에 묻는다. 지금 구현(`out/actor/GuardianWishApprovers`)은 자녀가 보낸 것 → 그 자녀의 보호자 1명(주문 자녀 복사본). 볼 수 있는 사람 = 보낸 사람 + 승인자(같은 가족의 다른 사람 403, 그 밖 404). 목록은 내가 보낸 것 + 내가 승인자인 것(`requestersApprovedBy`)
  - 보내기(로그인한 자녀만): 자기 장바구니 칸을 골라 `WishCart.reserveOwned`(→ 장바구니 `CartReservations.reserveOwned`: 주인 칸만, 결제 허용 = 승인자, 예약 ID = `wish-{조르기 ID}`) → `wish.sent`. 진행 중 조르기에 든 칸은 409(BEG-02, 조르기가 먼저 보고 장바구니 예약도 막는다)
  - 승인하고 결제: 조르기 API 없음. 승인자가 주문하기에 예약 칸 `cartItemId`를 넣어 주문한다(#998 장바구니 주문 확인 · 일부 칸 · 수량 조정). 결제 정리가 칸에서 산 수량만큼 빼며 낸 `cart.item-purchased`(예약 ID · 주문 ID · 주문상품 ID, #998)를 조르기가 받아(`WishPurchaseService`, 새 트랜잭션) 예약 ID(`wish-{id}`) · 칸 ID로 자기 예약 · 자기 칸이면 PAID + 결제한 사람 기록 + 남은 칸 예약 해제 + `wish_purchase`(주문 ID · 주문상품 ID `order_item_id`(이벤트에 없으면 null) · 칸) → `wish.paid`(조르기마다 1번). 같은 주문의 여러 칸 · 다시 받기 · 순서 바뀜도 1회분(`wish_purchase` 유일 + 상태). 이미 거절 · 철회된 조르기면 상태 · 이벤트는 그대로 두고 산 것만 남긴다(WARN). 결제 정리 뒤 조르기 반영 전의 거절 · 철회는 남은 예약 칸(`CartReservations.reservedCartItemIds`)이 줄보다 적거나, 칸이 남는 일부 수량 결제라도 장바구니가 그 예약에 결제 정리 표시를 남겼으면(`hasPurchase`) 409(`WISH_REQUEST_PURCHASE_IN_PROGRESS`). 조르기 예약 칸인데 이벤트에 주문 ID · 결제 회원이 없으면 건너뛰고 WARN(조르기 ID · 칸 ID). 결제되지 않으면 대기 그대로. 산 것의 수량(`wish_purchase.quantity`, 응답 `purchases[].quantity`)은 이벤트의 이번에 산 수량이다. 일부 수량만 결제해도 그 조르기는 결제 완료이고, 남은 칸은 예약이 풀려 자녀 장바구니에 남는다. 결제한 사람(`wish.paid` `payerId`)은 이벤트의 칸 결제 회원(`memberId`)이라 실제 결제자와 다를 수 있다
  - 수신(참모 결정 ①): Kafka로 받는다(결제 정리 트랜잭션과 분리, 조르기 실패가 결제를 되돌리지 않음). `wish/in/event/WishCartEventKafkaListener`가 자기 토픽 `kidly.order.events`를 주문 공용 수신 기반으로 구독한다(그룹 `kidly.order` · 팩토리 `orderKafkaListenerContainerFactory` · 재시도 → DLT `kidly.order.events.order.dlt`(주문 `OrderKafkaListenerConfig`가 선언, DLT 저장 · 다시 처리 대상). 조르기는 주문 코드를 참조하지 않으므로 그룹 · 팩토리 · 토픽은 값으로 같게 두고 테스트가 같은지 본다. DLT 다시 처리는 리스너가 내놓은 `Consumer<ConsumerRecord>` 빈으로). `cart.item-purchased`(예약 ID 있음)만 처리하고 다른 종류(사용자 빼기 `cart.item-removed` 포함)는 본문을 읽지 않는다. 예약 ID가 없는 구매 사실은 조르기와 무관해 건너뛴다. 주문 Kafka 수신 스위치가 꺼져 있으면(테스트 포함) `WishCartSpringEventReceiver`가 커밋 뒤 Spring 이벤트로 받는다(실패는 로그만, 결제로 번지지 않음)
  - 구매 표시와 조르기 반영이 어긋날 때: 장바구니가 예약에 결제 정리 표시(`purchased_at`)를 남겼는데 조르기 반영이 재시도 끝에 DLT로 가면 조르기는 대기(REQUESTED)로 남고 거절 · 철회는 계속 409(`WISH_REQUEST_PURCHASE_IN_PROGRESS`)다. DLT 다시 처리(관리자)로 반영되면 PAID가 되며 풀린다. #1008 만료도 같은 기준(빠진 칸 또는 `hasPurchase`)으로 결제 반영 중이면 건너뛰므로 대기로 남는다(DLT 다시 처리 뒤 PAID). 구매 표시와 예약 해제(거절 · 철회 · 결제 완료 뒤 해제)가 동시에 겹치면 예약 잠금(#1207, 아래 '예약 잠금 순서')으로 줄을 세워 먼저 잠근 쪽만 남는다: 거절 · 철회는 예약을 잠근 뒤 구매 표시(`hasPurchase`)를 보고 409(`WISH_REQUEST_PURCHASE_IN_PROGRESS`)
  - 거절(승인자, 사유) · 철회(보낸 사람, #968, 원인 DIRECT): 예약 해제 → `wish.rejected` · `wish.cancelled`(+ `cancelReason`). 칸은 장바구니에 남는다
  - 기한 만료(#1008, BEG-05): 설정 `kidly.order.wish.expiry`(enabled · ttl · interval · grace, 기본 true · P7D · PT1H · PT15M, `wish/app/config/WishExpiryProperties`). 유예 `grace`(0 이상): 만료 작업은 기한 + 유예가 지난 대기 조르기만 만료한다(`WishExpiry.isExpirable` · `sentBeforeExpirable`) — 기한 전에 만든 주문의 결제 완료가 늦게 와도 PAID로 반영되게. 기한 판정(`expiresAt` · 거절/철회 409 · 예약 `valid_until` = 새 주문 409)은 유예 없이 보낸 시각 + ttl. 유예는 결제 마감(`kidly.order.payment-timeout`)보다, 정확히는 결제 마감 + 결제 완료 전달(Kafka) 지연 여유보다 길게 둔다: 짧으면 `wish/in/scheduler/WishExpiryGraceCheck`(기동 작업)가 기동 때 WARN 한 줄(검증만, 조르기는 주문 코드를 모르므로 결제 마감은 설정 값으로만 읽는다). 기한은 저장하지 않고 보낸 시각 + 지금 ttl로 계산한다(`WishExpiry`, 응답 `expiresAt`은 대기 · 켜짐일 때만). `wish/in/scheduler/WishExpiryScheduler`(만료 스위치 · 조르기 스위치가 켜져 있을 때만 빈)가 자동 구매확정과 같은 방식(한 서버 잠금 · 순환 커서 · 대상 하나 = 트랜잭션 하나)으로 기한 지난 REQUESTED를 `WishExpiryService.expire`로 EXPIRED(`expired_at`) + 예약 해제 + `wish.expired`. 결제 반영 중(결제 정리로 빠진 칸이 있거나, 칸이 남는 일부 결제라도 예약에 구매 표시 `hasPurchase`가 있음)이면 만료하지 않고 건너뛴다(거절 · 철회 409와 같은 기준). 결제와 겹치면 예약 잠금 순서(#1207)로 줄을 세워 먼저 잠근 쪽이 이기고(결제 정리가 먼저면 만료는 잠근 뒤 구매 표시를 보고 예외 없이 건너뜀, 주기 작업은 다음 건 계속), 만료가 이기면 예약이 풀린 뒤라 그 결제는 조르기와 이어지지 않는다(구매 사실에 예약 ID가 없어 산 것에 남지 않고 상태 · 이벤트 그대로. 예약 ID가 실린 구매 사실이 만료 뒤에 오면 — 다시 처리 등 — 산 것만 남기고 WARN). 기한 지난 조르기의 거절 · 철회는 주기 작업 전이라도 409(`WISH_REQUEST_EXPIRED`, 이미 만료된 것도 같은 코드). 타임라인은 SENT → EXPIRED(시스템)
  - 결제 가능 기한(#1008, 사용자 결정 3 ①): 보낼 때 장바구니 예약에 `validUntil` = 만료 기한(`WishExpiry.reservationValidUntil`, 꺼져 있으면 null)을 넘긴다. 조르기는 기한을 저장하지 않고 장바구니 `cart_reservation.valid_until`은 그 계산값의 사본이다. 기한 지난 예약 칸의 보호자 주문은 만료 작업 전이라도 장바구니가 409(`RESERVATION_EXPIRED`). 설정(ttl · 켜짐)이 바뀌면 사본을 다시 맞춘다: `wish/in/scheduler/WishReservationValidUntilSync`가 앱이 뜰 때(ApplicationReadyEvent) 한 번, 만료 작업과 같은 잠금(`WishJobRunner`, 키 `kidly.order.wish-valid-until`)으로 한 서버에서만 진행 중(REQUESTED) 조르기 전부를 ID 커서 100건씩(배치 = 트랜잭션, `WishReservationValidUntilService`) `WishCart.updateValidUntil`로 갱신한다(꺼지면 null, 같은 값은 쓰지 않음). 설정은 기동 때만 바뀌므로 주기마다 돌지 않고, 만료가 꺼져도 돌아야 해서 만료 작업과 따로 둔다(조르기 스위치만 조건). 배치는 예약 잠금으로 결제 정리 · 예약 해제와 줄을 서 기다리고, 잠금 실패(교착 등, `ConcurrencyFailureException`)로 배치가 지면 그 배치만 조르기마다 자기 트랜잭션으로 다시 맞추고 또 지는 건은 건너뛴다(DEBUG, 다음 기동 때 다시). 실패해도 기동은 막지 않는다(WARN, 다음 기동 때 다시)
  - 조르기 API는 `@WishCaller`(wish `in/web` 해석기, `in/config.WishWebMvcConfig`로 등록, 공용 `@LoginMember` · `@LoginChild`는 그대로)로 회원 헤더면 회원, 회원 헤더 없이 자녀 헤더 둘이면 자녀(#906)를 받는다(둘 다 없거나 형식 오류 401, 자녀 계정 연결을 확인할 수 없으면 403 `CHILD_ACCOUNT_FORBIDDEN`). 장바구니 `@CartCaller`와 규칙이 같다(컨텍스트별 복사). 경로 `/api/v1/wish/requests`(· `/{id}` · `/{id}/rejection` · `/{id}/cancellation` · `/{id}/timeline`). 타임라인은 SENT → PAID · REJECTED · CANCELLED와 산 주문 ID(조르기는 주문 타임라인을 읽지 않는다)
  - 데이터(#999 `V202611062100`, 두 번 적용 안전): 진행 중 조르기는 CANCELLED(SYSTEM), 바로 결제가 결제된 조르기는 PAID, `wish_item` 표와 `wish_request_line.wish_item_id` · 승인 단계 칸(checkout · order_id · order_result · decided_*)은 지운다. 만료(BEG-05)는 #1008
  - 결제된 주문상품 ID(#1000): 조르기 목록 · 상세 응답의 `paidOrderItemIds`는 `wish_purchase.order_item_id`(cart.item-purchased의 `orderItemId`, 없으면 빠짐)다. 화면이 주문의 자녀 구매 내역(`GET /api/v1/orders/items/mine`)과 맞춰 출처를 표시한다. 조르기는 주문을 읽지 않는다(wish → order 의존은 모듈 공용 기반 두 포트뿐)
- 컨텍스트 사이는 in · out으로만 잇는다(#641, `api` 패키지는 두지 않는다). 받는 쪽은 들어오는 포트를 자기 `app.port.in`에 두고 app이 구현한다(`OrderLookup` · `DeliveryRecorder` · `ReplicaLookup` · `OrderEventIssuer` · `CartCleanup` · `CartReservations` · `CartCheckout` · `DeliveryOperations` · `ShippingDelays`). 부르는 쪽은 필요한 것을 자기 `app.port`에 자기 말로 두고(`OrderDeliveries` · `OrderedCartCleaner` · `OrderCartLines` · `CartCatalog` · `DeliveryOrders` · `WishCatalog` · `WishCart` · `CartEvents` · `WishEvents` · `DeliveryEvents`), `out.{상대}` 어댑터가 상대 `app.port.in`을 불러 값을 옮겨 담는다. 다른 컨텍스트를 아는 것은 이 어댑터뿐이다(app · domain · in은 모른다). 같은 앱 안의 동기 호출이라 부르는 쪽 트랜잭션에 합류한다. 예외는 두지 않는다(멈춘 주문의 발송 지연도 `OrderDeliveries`로 읽는다). 떼어 낼 때는 어댑터를 HTTP · Kafka 호출로, 받는 쪽은 `app.port.in`을 부르는 컨트롤러 · 리스너를 in에 더한다
- 컨텍스트마다 시각 기반 클래스(`OrderTimeEntity` · `CartTimeEntity` · `DeliveryTimeEntity` · `WishTimeEntity`) · 규칙 예외 · 오류 코드(`OrderErrorCode` · `CartErrorCode` · `DeliveryErrorCode` · `WishErrorCode`)를 따로 둔다. 같은 오류는 응답(상태 · title · detail)이 같게 둔다
- `domain`: 업무 규칙 · 불변식(엔티티 · 상태 enum · 값, JPA 엔티티 겸용). 상태 · 값을 보고 하는 업무 판단(취소 가능 · 결제 반영 결과 · 수량 상한 · 재처리 상태 등)은 domain 메서드가 하고 app은 순서만 조율한다. 기술 장치(아웃박스 메시지 · DLT 보관 · Kafka 대기량 확인 결과)는 domain 밖(out · app.port 값)에 둔다(#642). Spring과 `common`을 쓰지 않는다. 상태는 업무 메서드로만 바꾸고, 다시 와도 되는 변경은 `TransitionResult`(`APPLIED` · `ALREADY_DONE` · `NOT_APPLICABLE`)로 돌려준다
- `app`: 유스케이스 서비스. 기능별 하위 패키지(`order` · `outbox` · `deadletter` · `provided` 등)끼리는 서로 의존하지 않는다. 공통 설정 값은 `app.config`로 읽는다. 여러 기능이 같이 쓰는 값은 `app` 바로 아래(`OrderActor` · `OrderErrorCode` · `OrderLogContext`)에 둔다. 주문의 들어오는 포트 구현은 `app.provided`(`ProvidedOrderService` · `ProvidedReplicaService`)이고, 주문을 취소하는 판매자 취소 포트(`SellerCancelService`, 대기 기록 닫기 `WaitingRecordCloser`가 거기 있어서)만 `app.order`다. 장바구니 · 배송의 구현은 `CartService` · `DeliveryService`다

- 순환 금지(#998, `OrderContextArchitectureTest`): 장바구니는 주문을 참조하지 않는다. 예외는 모듈 공용 기반인 주문의 복사본 조회(`ReplicaLookup`) · 이벤트 발행(`OrderEventIssuer`, 아웃박스) 포트뿐이고, 나중에 공용 컨텍스트로 옮긴다. 주문 · 장바구니 · 배송은 조르기를 참조하지 않는다. 조르기 → 주문(바로 결제 · 보호자 장바구니 옮기기)은 #999에서 없앤다

## 2. 이벤트 수신
- 복사본 반영(#738)은 종류 · 대상 ID별 트랜잭션 advisory lock(`ReplicaUpdateLock`, `out.lock.ReplicaAdvisoryLock`)을 조회 전에 잡고 커밋 · 롤백까지 유지한다. 행이 없는 최초 생성도 직렬화하고, 상품은 상품 ID 하나로 전체 옵션 · 누락 옵션 처리를 묶는다. 자녀 변경 · 삭제는 같은 잠금을 쓴다. 이 잠금은 스케줄러의 한 서버 실행 잠금과 별개다.
- 같은 이벤트가 다시 와도 결과는 1회분이다: 복사본(`ReplicaProduct` · `ReplicaSeller` · `ReplicaChild`)은 저장된 `occurredAt`보다 늦은 이벤트만 반영하고, 주문 상태는 이미 그 상태면 `ALREADY_DONE`으로 끝낸다
- 프로필 없는 자녀 삭제(#739)도 `replica_child`에 자녀 ID · 보호자 ID · 삭제 시각을 남긴다. 키 · 몸무게는 삭제 행에서만 비어 있을 수 있다(DB CHECK). 과거 · 동일 시각의 활성 이벤트는 무시하고, 더 최신의 정상 프로필은 기존 최신 이벤트 우선 정책대로 반영한다. 자녀 복사본 시각은 DB 정밀도(마이크로초)로 잘라 저장 · 비교한다.
- 필수 값이 없으면 `EventGuard`로 WARN 한 줄을 남기고 무시한다
- 상품 · 재고 · 결제의 받는 길은 `kidly.order.kafka.consumer.enabled`가 `true`(기본)면 Kafka, `false`면 Spring 이벤트(`SpringEventReceiver`)다. 판매자 · 자녀 · 자녀 계정(`kidly.auth.events`의 `child-account.changed`, #906)은 Kafka로만 받는다. 자녀 계정 복사본(`replica_child_account`)은 삭제가 한 방향(있음 → 삭제, 삭제 뒤 예전 생성 무시)이고 삭제되지 않은 계정은 늦은 메시지만 반영한다(시각은 마이크로초, 복사본 잠금 `CHILD_ACCOUNT`). 같은 토픽의 `auth.tokens-revoked`는 받지 않는다. 회원 탈퇴(`kidly.member.events`의 `member.withdrawn`, #1001)도 Kafka로만 받는다(`MemberEventKafkaListener`, DLT `kidly.member.events.order.dlt`, 다른 회원 이벤트는 건너뜀)
- 삭제 · 탈퇴 정리(#1001): 정리로 칸을 지울 때는 `cart.item-removed`를 내지 않는다(장바구니 `CartCleanup.removeOwnerItems`, 주문 쪽 포트 `CartOwnerCleaner`). 삭제 · 탈퇴는 한 방향이라 여러 번 · 순서가 바뀌어 와도 결과가 같다
  - 자녀 삭제(`child.changed` deleted): 복사본 반영(`ReplicaService`) 뒤 복사본이 삭제 상태면 그 자녀 프로필이 주인인 CHILD 칸을 지운다(예약 칸 포함). 더 최신 정상 프로필로 되살아난 복사본이면 지우지 않는다. 결제된 · 결제대기 주문은 그대로(원래 흐름)
  - 자녀 계정 삭제(`child-account.changed` deleted): 계정 복사본이 삭제 상태면 그 계정의 자녀 프로필이 주인인 CHILD 칸을 지운다(주인 = 프로필, 계정이 없으면 쓸 사람이 없다)
  - 두 삭제 모두 반영 뒤 받은 이벤트를 앱 안 Spring 이벤트로 다시 알리고(`EventPublisher`, 아웃박스 아님) 조르기(`wish/in/event/WishDeletionEventReceiver`, 같은 트랜잭션 `@EventListener`)가 그 프로필이 보낸 대기 조르기를 CHILD_DELETED · ACCOUNT_DELETED로 철회 · 예약 해제 · `wish.cancelled`. 주문은 조르기를 모르고, 같은 Kafka 메시지를 조르기 리스너가 같은 그룹으로 또 받으면 파티션이 나뉘므로 이렇게 잇는다. 조르기가 실패하면 함께 롤백 → Kafka 재시도
  - 회원 탈퇴(`MemberWithdrawalService`): 결제대기 주문을 구매자 취소와 같은 전이(사유 BUYER_CANCELLED)로 취소하고 `order.cancelled`(이력 주체 SYSTEM · 출처 `member.withdrawn`), 회원 장바구니(MEMBER 주인)를 지운다. 결제 · 배송 중 주문은 그대로. 자녀 쪽은 자녀 삭제 이벤트로 정리된다. 탈퇴 회원이 승인자인 진행 중 조르기는 이번 범위가 아니다(자녀 삭제로 철회됨)
- Kafka 리스너(`ProductEventKafkaListener` · `SellerEventKafkaListener` · `ChildProfileEventKafkaListener` · `PaymentEventKafkaListener` · `AuthEventKafkaListener`(#906))는 팩토리 `orderKafkaListenerContainerFactory`(`OrderKafkaListenerConfig`)만 쓴다: 한 건씩 완료, 처음 읽는 그룹은 earliest, 실패하면 1초 간격 3번 재시도 뒤 `{토픽}.order.dlt`, 다시 해도 같은 예외 · 읽기 실패는 바로 DLT. 결제 완료는 DLT로 보내기 전에 `payment_recovery` 보관을 한 번 더 시도하고, 보관되면 보내지 않는다(`PaymentEventKafkaListener.keepAfterRetries`)
- 처리 실패를 주문이 보관하면 리스너가 처리 완료로 본다. 재고 차감됨 · 재고 차감 실패 · 결제 실패는 `EventFailureKeeper.run`이 `order_event_failure`에, 결제 완료는 `PaymentEventListener`가 `payment_recovery`에 보관하고, 둘 다 `EventFailureKeeper.markHandled`로 처리 완료 표시를 붙인다. 관리자가 재처리 · 종료한다. 보관까지 실패하면 재시도 → DLT. 결제 완료의 동시 처리에서 진 쪽은 주문이 아직 결제대기면 보관 없이 재시도하고, 재시도가 끝나면 위처럼 보관한다(재처리 대기 주문은 결제 마감 만료가 취소하지 않는다)
- DLT 메시지는 `OrderDeadLetterKafkaListener`가 `order_dead_letter`에 원래 위치(토픽 · 파티션 · 오프셋)당 1건으로 저장한다. 저장 실패는 DLT로 다시 보내지 않고 끝없이 재시도한다. 관리자 재처리는 저장한 본문으로 원래 리스너를 그대로 부른다(원래 토픽에 다시 넣지 않음)
- 주문이 취소되면 그 주문의 재처리 대기 기록을 같은 트랜잭션에서 닫는다(`WaitingRecordCloser`, 이유 `ORDER_CANCELLED`)

## 3. 이벤트 발행과 주기 작업
- 주문 이벤트는 루트 규칙대로 `EventPublisher`로 발행하고, 같은 트랜잭션에서 `order_outbox`에 저장된다(`OrderOutboxWriter`). 업무가 롤백되면 메시지도 남지 않는다
- 결제완료로 실제로 바뀌면(이벤트 수신 · 관리자 결제 복구) `order.paid`(`OrderPaidEvent`, 키 = 주문 ID, 스냅샷 상품명 · 옵션명 · 판매자, 배송지 제외, #899)를 같은 트랜잭션에서 아웃박스로 낸다(`OrderService.markPaid`). 이미 결제완료 · 취소 뒤 결제 · 주문 없음은 내지 않고, 배송 생성 · 장바구니 정리가 실패해 되돌려지면 남지 않는다
- 배송 출발(ship) · 완료(수동 complete · 택배 조회 completeByTracking, 이미 완료면 없음) 때 `delivery.shipped` · `delivery.delivered`(`DeliveryShippedEvent` · `DeliveryDeliveredEvent`, 키 = 주문 ID, 구매자 ID는 `DeliveryOrders`로 주문에서 읽음, carrier 코드 + carrierName, 배송지 · 수령인 없음, #900)를 `delivery/app/port/DeliveryEvents` → `delivery/out/order` 어댑터 → `OrderEventIssuer`로 같은 트랜잭션에서 낸다. 주문이 없으면 상태 변경은 그대로 두고 이벤트 없이 WARN 한 줄. `delivery.delivered`는 #1061부터 `autoConfirmAt` · `items`를 더 싣는다: 두 완료 경로 모두 `DeliveryService.publishDelivered` 한 곳에서 `DeliveryOrders.recordDelivered`(→ 주문 `DeliveryRecorder.recordDelivered`)가 돌려준 그 판매자 몫 주문상품(취소 제외)으로 채운다. 예정 시각은 `OrderItem.autoConfirmAt`(= 주문상품 deliveredAt + `Order.Policy.autoConfirmAfter`)으로 `Order.autoConfirmItem`과 같은 기준이고, 한 배송의 주문상품은 같은 배송 완료 시각이라 같다(다르면 가장 이른 값, 주문상품이 없으면 null · 빈 목록)
- 장바구니는 담기에 성공하면(새 줄 · 같은 줄 합치기) `cart.item-added`(`CartItemAddedEvent`, 키 = 회원 ID), 사용자가 줄을 빼면 `cart.item-removed`(`CartItemRemovedEvent`, 키 = 회원 ID, quantity = 뺄 때 줄 수량, #709), 결제완료 정리(`clearOrdered`)로 산 칸을 지우면 칸마다 `cart.item-purchased`(`CartItemPurchasedEvent`, 키 = 회원 ID, `quantity` = 이번에 산 수량(칸에 남은 수량 아님) · `orderId` · `orderItemId`(산 주문상품, 주문이 정리 줄을 넘길 때 실음) · 예약 칸이었으면 `reservationId`, #998)를 같은 길로 낸다: `cart/app/port/CartEvents` → `cart/out/order` 어댑터 → 주문 `app/port/in/OrderEventIssuer`(구현 `ProvidedEventService`, #654). 결제 정리는 `cart.item-removed`를 내지 않는다. 세 이벤트 모두 장바구니 주인 `ownerType` · `ownerId`를 싣고 memberId · 키는 줄의 결제 회원(자녀 주인이면 보호자, 실제 결제자와 다를 수 있음)이다. 수량 변경은 내지 않는다. 받는 도메인에 맞춘 필드는 넣지 않는다
- 조르기는 보내기 · 결제 완료 · 거절 · 철회 · 만료에 성공하면 `wish.sent` · `wish.paid`(#999, 조르기마다 1번, + 결제한 사람 · 주문 ID) · `wish.rejected` · `wish.cancelled`(#968, + 원인 `cancelReason` #999) · `wish.expired`(#1008, 시스템 만료)(`shared.order.event.Wish…Event`, 키 = 자녀 프로필 ID, data = 조르기 ID · 자녀 · 보호자 회원 ID · items[productId · optionId · quantity] · 거절 사유)를 같은 길로 낸다. `wish.approved` · `wish.item-added`는 #999에서 보내지 않는다(이벤트 클래스는 shared에 남김). 내는 길: `wish/app/port/WishEvents` → `wish/out/order` 어댑터 → `OrderEventIssuer`(#702). 실패 · 롤백 · 동시 처리에서 진 쪽은 이벤트가 남지 않는다. 사실만 담고 문구 · 개인정보는 넣지 않는다
- 관리자 멈춘 주문(아웃박스 멈춤)은 eventType 접두(`order.` · `order-item.` · `delivery.`(#900))로 메시지 키가 주문 ID인지 판별한다 — 새 주문 이벤트 종류가 이 접두를 벗어나면 `StuckOrderService` 목록을 같이 고친다
- `OrderOutboxRelayScheduler`가 전송 가능한 메시지를 한 트랜잭션에서 id 순서로 batch만큼 보낸다(`KafkaOrderEventSender`). 타임아웃 · 연결 · 인증 · 알 수 없는 실패는 전송 여부가 불명확하거나 환경 문제이므로 기존처럼 그 자리에서 멈추고 재시도한다. 횟수가 많다는 이유로 격리하지 않는다.
- 아웃박스 영구 실패 격리(#740): Kafka가 크기 초과(`RecordTooLargeException`)로 거절한 경우만 격리한다. 같은 토픽 · 메시지 키의 후속 행은 같은 배치에서도 건너뛰고, 다음 조회에서도 LIMIT 전에 제외한다. 다른 키는 계속 보낸다. 순서 기준은 기존 Kafka 계약의 `(topic, correlationId)` 그대로다. 다른 업무라도 토픽 · 숫자 키가 같으면 보수적으로 함께 보류한다. 이벤트 ID · 본문 · 키는 바꾸지 않는다.
- 보낸 뒤 DB 커밋이 실패하면 격리 · 보냄 기록이 함께 롤백되므로, 다음 실행에서 같은 이벤트 ID로 다시 보낸다(at-least-once). 받는 쪽의 기존 멱등 처리가 필요하다. 보낸 행만 기존 보관 기간 뒤 정리하며, 격리 행과 그 후속 행은 지우지 않는다.
- 주기 작업(결제 마감 만료 · 자동 구매확정 · 아웃박스 릴레이 · 정리)은 `SingleServerJobRunner`로 한 번에 한 서버에서만 돈다(PostgreSQL advisory lock `kidly.order.{작업}`). 작업은 잠금 트랜잭션 밖에서 돈다. 조르기 만료(#1008)는 조르기 컨텍스트의 같은 방식 복사본(`wish/app/port/WishJobRunner` · `wish/out/lock/WishAdvisoryLockJobRunner`, 잠금 `kidly.order.wish-expiry`)으로 돈다. 예약 기한 다시 맞추기(`WishReservationValidUntilSync`, 잠금 `kidly.order.wish-valid-until`)는 주기 없이 기동 때 한 번 같은 잠금 방식으로 돈다. 처음 실행은 기동 한 주기 뒤라(initialDelay = interval) 배포 직후 최대 한 주기 동안 예약 해제가 늦을 수 있다(409 판정은 계산이라 영향 없음)
- 멈춘 주문 AI 진단(#926, `StuckOrderDiagnosisScheduler`, 주기 `kidly.order.ai.interval`, 잠금 `kidly.order.stuck-diagnosis`): 기동 직후에는 부르지 않고(첫 실행도 주기 뒤), 스케줄러 스레드(아웃박스 릴레이와 같이 씀)를 AI 대기로 막지 않게 전용 스레드 하나에 넘기고 바로 돌아온다(앞 실행이 돌면 건너뜀). `StuckOrderDiagnosisService`가 관리자 조회와 같은 `StuckOrderService`로 종류마다 멈춘 대상을 오래된 것부터 `scan-size`씩 읽고(요청 상한이 남으면 다음 페이지를 `max-scan-pages`까지 — 앞쪽이 모두 메모가 있어도 뒤쪽 새 건에 닿는다), 페이지마다 마지막 이력 ID · 이미 요청한 상태를 쿼리 한 번씩으로 읽어 (주문, 종류, 마지막 상태 이력 ID)로 이미 요청한 건 (성공 · 실패 모두)은 건너뛴다 = 상태가 바뀌기 전까지 한 번. 하루 상한(`daily-limit`, DB의 오늘 요청 수) · 한 실행 상한(`max-per-run`) 안에서만 부르고, AI 호출은 트랜잭션 밖이다(메모 저장만 자기 트랜잭션). 단 한 실행 동안 잠금(advisory lock) 연결을 쥐고 있어, 그 시간은 대략 `max-per-run` × `timeout`(기본 10 × 15초)이다(잠금 연결은 서버당 최대 2개: 스케줄러 + 진단 전용 스레드). `timeout`은 읽기 제한(소켓 읽기 한 번마다)이고, 느리게 조금씩 오는 응답은 서킷브레이커의 느린 호출 기준이 잡는다. 요청에는 출력 상한(`max-output-tokens`, max_completion_tokens)을 넣고 응답 본문은 64KB까지만 읽는다(넘으면 BAD_RESPONSE). 어댑터가 약속을 어긴 결과(성공인데 칸 빠짐 등)는 서비스가 FAILED(BAD_RESPONSE)로 바꾼다. 실패 · 시간 초과 · 형식 오류는 FAILED 메모로 남기고 계속, 서킷 열림 · 꺼짐은 기록 없이 그 실행을 멈춘다. 주문 · 결제 · 취소 흐름은 AI를 부르지 않는다. AI 요청에는 주문 쪽 값(종류 · 상태 · 이력의 대상/상태/사유/주체 종류/출처 · 실패 · 복구 · 아웃박스 기록 코드)만 넣고 개인정보 · 주체 ID를 넣지 않는다. AI 요청의 자유 문구는 `app.OrderTextGuard`로 거른다(#925 MCP와 같은 규칙: 상태 · 재고 사유는 대문자 코드, 이력 사유 · 실패 코드는 실패 코드 형식, 이력 출처 · 아웃박스 eventType은 경로 틀 · scheduler · 이벤트 타입, 아웃박스 마지막 전송 실패는 예외 클래스 이름만). 형식 밖이면 null이고 프롬프트에서 그 칸을 뺀다. 로그에는 이유 코드 · 상태 · 제공자 호스트 · 모델만(프롬프트 · 응답 본문 · 키 없음)
- 주기 작업(결제 마감 만료 · 자동 구매확정 · 택배 조회 · 조르기 만료)은 메모리 순환 커서(`RotatingCursor`, #656)로 지난 실행이 상한(max-per-run)에서 멈춘 곳 다음부터 이어 읽고 끝에 닿으면 처음으로 돌아간다(서버마다 따로, 재기동하면 처음부터). 상한에 닿고 남은 대상이 있는 실행의 실행 로그는 WARN 한 줄이다
- 결제 마감 만료 · 자동 구매확정(`OrderScheduler`)은 대상 주문 하나 = 트랜잭션 하나다. 한 건이 실패해도 로그만 남기고 다음 건을 처리한다
- 결제 마감 만료는 결제 이벤트를 Kafka로 받는 동안 처리 대기분이 있으면 그 주기를 건너뛴다(`PaymentExpiryGate`)
- 배송 자동 완료(#650): `DeliveryStatusPoller`가 발송 중이고 조회를 멈추지 않은 배송을 `DeliveryStatusChecker`(out `tracker`, Delivery Tracker)로 트랜잭션 밖에서 조회하고, 택배사 DELIVERED이고 택배사 시각 > 발송 시각일 때만 `Delivery.completeByTracking`으로 완료한다(완료 시각 = 택배사 시각, 이력 SYSTEM · `scheduler:delivery-tracking`, 수동 완료와 겹쳐도 1회). 운송장 형식 오류는 `tracking_stopped_at`으로 조회를 멈추고(수동 완료는 가능) 그 밖의 오류는 다음 주기에 다시 본다. 한 서버에서만(`DeliveryJobRunner`, 잠금 `kidly.delivery.{작업}`), 인증값이 없으면 기능만 꺼진다. 택배 조회 호출은 서킷브레이커(#708, Resilience4j 코어만 · 주문 build 파일에만, 스타터 · 전역 `resilience4j.*` · 빈 없이 `out/tracker/TrackerCircuitBreaker`가 만들어 씀, 설정 `kidly.order.delivery-tracker.circuit-breaker.*`)를 거친다: 네트워크 · 타임아웃 · 5xx · 인증 · 호출 한도 등은 실패, 형식 오류 · 없는 번호는 세지 않는다. 열려 있으면 부르지 않고(호출 간격도 안 기다림) UNAVAILABLE(`CIRCUIT_OPEN`)로 다음 실행에서 다시 조회하며, 로그는 상태가 바뀔 때만 한 줄(열림 WARN, 반열림 · 닫힘 INFO)이고 건너뛴 건은 DEBUG다
- 판매자 발송 전 부분 취소(#655, 스위치 `kidly.order.partial-cancel.enabled` 기본 켜짐(#924)): `Delivery.cancelBySeller`(READY만) → `delivery/out/order` 어댑터 → 주문 `app/port/in/SellerItemCancellation`(구현 `app.order.SellerCancelService`)이 주문을 FOR UPDATE로 읽고(동시 취소 직렬화, 주문 → 배송 잠금 순서) `Order.cancelSellerItems`로 그 판매자 주문상품을 CANCELLED, 모두 취소면 주문도 CANCELLED(`SELLER_CANCELLED`)로 바꾸고 취소 기록(`order_item_cancellation`, ID = cancellationId) · 이력 · `order-item.cancelled`(키 = 주문 ID)를 한 트랜잭션으로 남긴다. 이때 `order.cancelled`는 보내지 않고, 주문이 취소됐으면 재처리 대기 기록을 닫는다. 취소된 주문상품은 배송 완료 기록 · 구매확정 · 자동 구매확정 · 멈춘 주문에서 빠진다
- 판매 불가 판매자 정리(#1121): `seller.changed`를 받아 판매자 복사본에 반영한 뒤(트랜잭션 커밋 뒤, 모르는 판매자 상태는 팀 Kafka 규칙대로 재시도 없이 DLT) `app.order.SellerUnavailableCleanupService`가 복사본의 지금 상태가 `ACTIVE`가 아니면(판단은 이것 하나, 다른 값을 코드에 적지 않음 · 복사본 없으면 안 함) 그 판매자 상품의 ORDERED 주문상품이 든 결제대기 · 결제완료 주문을 ID 커서 100건씩 읽어 주문마다 트랜잭션으로 `OrderService.cancelForUnavailableSeller`를 부른다. 결제대기는 `Order.cancelForSellerUnavailable`로 주문 전체 취소(`SELLER_UNAVAILABLE`, `order.cancelled`, 부분 취소 대신 전체 · 사유 하나는 #1121 결정), 결제완료는 `OrderDeliveries.cancelForUnavailableSeller` → 배송 `DeliveryOperations.cancelForUnavailableSeller`가 그 판매자 배송이 READY일 때만 판매자 발송 전 취소와 같은 경로(배송 CANCELLED + `SellerItemCancellation`, 주문상품 사유 `SELLER_UNAVAILABLE`, `order-item.cancelled`)로 취소한다(부분 취소 스위치와 무관). 그 몫으로 주문의 모든 주문상품이 취소되면 주문 사유도 `SELLER_UNAVAILABLE`이다(판매자가 스스로 취소한 `SELLER_CANCELLED`와 구분, `Order.cancelSellerItems`가 주문상품 사유로 정한다). 배송 중 · 배송 완료 · 이미 취소는 그대로라 다시 받거나 순서가 바뀌어도 1회분이다. 주체는 SYSTEM · 출처 `seller.changed`(회원 탈퇴 #1001과 같음). 실패한 주문이 있으면 끝에 예외 → Kafka 재시도. 새 주문은 막지 않는다(상품 판매중지가 막음). 사유 칸 허용 값은 `V202611101400`이 넓혔다.

- 구매확정 사실 복구(#741): `POST /api/v1/admin/orders/purchase-confirmed-events`는 주문 DB의 CONFIRMED 주문상품만 기존 `order-item.purchase-confirmed` 계약으로 재발행한다(저장된 confirmType 포함, 없으면 null, #901). 다른 스키마를 읽지 않고, 실제 confirmedAt · 주문 키 · 스냅샷을 유지한다. 새 eventId로 같은 사실을 재전달하므로 수신자는 주문상품 ID 기준 멱등성을 지켜야 한다(현재 정산 · 추천 · 커뮤니티가 해당 규칙을 사용한다).
- 복구는 afterOrderItemId(기본 0) · size(1~100) 커서 배치이고 첫 응답의 throughOrderItemId를 다음 요청에도 유지한다. hasNext가 참이면 nextAfterOrderItemId로 이어 간다. 발행 수는 아웃박스 저장 수이며 실제 수신 완료 수가 아니다. 스캔 중 커서보다 작은 ID가 뒤늦게 확정되면 정상 확정 이벤트로 처리되고, 필요하면 같은 범위를 다시 스캔한다. 요청 실패 시 그 배치의 아웃박스도 롤백된다.

- 운영 지표(#1067, `kidly.order.*`, 태그는 고정 값만): 적체 게이지는 `order/app/OrderBacklogGauges`(DLT OPEN · 이벤트 실패 PENDING · 결제 복구 PENDING · 아웃박스 미전송 · 가장 오래된 미전송 나이 · 격리, 격리 제외 기준 · 멈춘 주문 종류별 = 관리자 요약, 30초 캐시), 주기 작업 마지막 성공 시각 · 아웃박스 전송 실패 카운터는 `order/app/OrderOperationMetrics`(app 기능 slice끼리 참조하지 않게 app 바로 아래). 배송 · 조르기는 같은 이름(`kidly.order.scheduler.last.success.seconds{job}`)을 자기 컨텍스트(`delivery/app/DeliveryJobMetrics` · `wish/app/WishJobMetrics`)에서 등록한다. 성공은 이 서버가 잠금을 잡고 끝까지 돌았을 때만(건별 실패는 성공, 예외 · 다른 서버 · 릴레이 STOPPED · 결제 만료 실행 조건으로 건너뜀은 아님, 첫 성공 전 NaN). 택배 조회 서킷 상태는 `DeliveryTrackerChecker.bindCircuitState`가 직접 등록한다(지금 상태만 1). 아웃박스 전송 실패 카운터의 태그는 `event_type`(이벤트 타입) · `outcome`(retry · quarantined)뿐이다. Kafka 보내기가 꺼져 있으면(`kidly.kafka.producer.enabled=false`, 릴레이 빈 없음) `outbox_relay`, 택배 조회 인증값이 없으면 `delivery_tracking`, 조르기 만료가 꺼져 있으면 `wish_expiry` 작업 시각은 계속 NaN이다

## 5. 관리자 확인 대상
- 관리자 화면 · 목록 · WARN/ERROR 로그에는 사람이 실제로 조치해야 하는 것만 남긴다
- 격리 아웃박스(#740): `GET /api/v1/admin/orders/outbox/quarantined`(id 순, page · size 1~100) · `GET /api/v1/admin/orders/outbox/{id}`는 본문 없이 메타데이터만 보여 준다. 격리 시 WARN 한 줄을 남기고, 격리 중인 행을 주기마다 다시 보내거나 경고하지 않는다. `OUTBOX_STUCK` 대표 항목은 전송 가능한 미전송 맨 앞이 시간 · 시도 기준을 넘으면 먼저 표시한다. 그런 대기가 없으면 가장 오래된 격리를 임계값 없이 즉시 표시한다. 격리가 일반 전송 장애를 가리지 않게 한다. 전체 격리는 새 목록에서 본다. 격리 항목의 backlog는 같은 토픽 · 키의 후속 미전송 건수이고, 일반 장애 항목은 기존 전체 backlog다.
- 운영자는 격리 원인(메시지 크기와 생산자 · 토픽/브로커 한도)을 확인해 해결한 뒤 `POST /api/v1/admin/orders/outbox/{id}/retry`로 같은 이벤트를 전송 대기시킨다. 재시도자 · 시각 · 횟수를 기록하고 원본 · 전송 시도 이력은 유지한다. 이미 대기 중이면 변경 없이 200, 이미 보냈으면 409, 없으면 404다. 정상 전송까지 같은 키의 후속 순서는 유지된다. 다시 거절되면 다시 격리된다.
- 이벤트를 건너뛰어 결제 · 재고 · 리뷰 등의 사실을 잃지 않도록 격리 행의 폐기/보냄 처리 API는 두지 않는다. 해결 전에는 해당 키를 계속 보류한다. 알림·조치는 격리 WARN과 관리자 목록/OUTBOX_STUCK을 기준으로 한다.
- DLT 메시지 목록은 상태를 주지 않으면 `OPEN`만 보인다(처리 · 종료된 건은 상태로 걸러 본다). 결제 토픽에서 온 메시지가 먼저 온다(`paymentEvent`). 이벤트 처리 실패 · 결제 반영 실패 목록은 상태를 주지 않으면 모든 상태가 보인다
- 이미 해결됐거나 저절로 맞춰지는 건은 그 자리에서 닫거나(예: 주문 취소 시 대기 기록) 로그 수준을 내린다(예: 같은 메시지의 반복 저장 실패는 첫 번만 ERROR, 이후 DEBUG)
- 로그는 결과 하나에 한 줄이고, 본문 · 예외 메시지 · 개인정보를 넣지 않는다(eventType · eventId · 키 · ID · 예외 종류만)
- 주문 운영 조회 MCP 창구(#925, `POST /api/v1/admin/orders/mcp`, 도구 목록은 docs/api): AI가 위 관리자 확인 대상을 읽기만 한다. 도구는 관리자 조회 API(`web.admin`)가 쓰는 app 조회 서비스만 부르고 응답 칸도 관리자 API와 같게 둔다(새 조회가 필요하면 app에 먼저 더한다). 조작(재처리 · 종료 · 취소 · 다시 보내기) 도구는 두지 않는다. 응답에 개인정보(배송지 · 연락처 · 수령인 · 닉네임 · 자녀 정보)와 DLT 원본 본문 · 관리자 메모 · 예외 메시지 · 스택을 넣지 않는다(DLT 실패는 예외 종류만). 자유 문구는 코드 · 예외 클래스 이름만: 자유 문구가 될 수 있는 칸(아웃박스 lastError · 이력 reason/source · 실패 코드 · DLT의 받은 키/ID/producer/eventType · 재처리 결과)은 MCP 전용 변환(`in.mcp.OrderMcpViews` · `OrderMcpDeadLetter`)이 `app.OrderTextGuard`로 걸러 정해진 형식일 때만 내보내고 아니면 null이다(관리자 API는 그대로). 형식은 실제로 만들어지는 값만 통과하게 좁게 둔다: 예외 이름은 `…Exception`/`…Error`, 코드는 대문자로 시작, 줄표 코드는 결제 불일치 사유 목록, 숫자 ID는 0으로 시작하지 않음, DLT 키 · aggregateId · correlationId는 관련 주문 ID와 같거나 UUID, producer는 원래 토픽 `kidly.{x}.events`의 x와 같을 때만, eventType은 앞 마디가 토픽별 허용 목록(`OrderTextGuard.RECEIVED_EVENT_PREFIXES`, 기본 x · product 토픽은 product. · stock. · childprofile 토픽은 child. · auth 토픽은 child-account.(auth.tokens-revoked 제외), 구독 토픽이 늘면 더한다)에 있을 때만, '자체 보관으로 넘김'은 `HANDED_OFF`(`DeadLetterHandling.isHandedOff`). 밖으로 내보내는 다른 창구(AI 진단 #926 등)도 같은 `OrderTextGuard`를 쓴다
  - 스위치 `kidly.order.mcp.enabled`(기본 false, 꺼지면 빈 · 경로 없음), 목록 줄 수 상한 `kidly.order.mcp.max-results`(기본 50, 큰 size는 줄인다)
  - 구성: MCP 공식 Java SDK(주문 build에만), 상태 없는 서블릿 전송 + 동기 서버를 `in.config.OrderMcpConfig`가 서블릿으로 등록한다. MVC 밖이라 `in.mcp.OrderMcpServlet`이 `X-Admin-Id`를 공용 LoginAdmin 해석기와 같은 규칙으로 직접 확인한다(없거나 잘못되면 401 ProblemDetail). JSON은 Boot의 JsonMapper를 감싸 쓴다. 도구 실패 로그는 도구 이름 · 예외 종류만
- 멈춘 주문 목록의 `aiMemo`(#926)는 AI의 제안일 뿐이다(조치는 관리자가 기존 API로). (주문, 종류)별 가장 최근 성공 메모만 붙이고, 없거나 실패만 있으면 null이다. 진단이 꺼지거나 실패해도 멈춘 주문 목록 · 요약은 그대로다. 스위치 `kidly.order.ai.enabled`(기본 false, 키 없으면 꺼짐)

## 6. 로그 추적(MDC)
- Kafka 수신 · 아웃박스 릴레이 · 주문 스케줄러는 메시지 · 대상 하나를 처리하는 동안 `OrderLogContext`로 MDC에 추적 값을 넣고, 끝나면(예외 포함) 이전 값으로 되돌린다
- 요청 밖이라 `traceId`가 비어 있으면 `correlationId`를 넣는다. HTTP 요청 안에서는 요청의 `traceId`를 그대로 둔다
- Kafka 수신은 팩토리의 `OrderLogContextRecordInterceptor`(헤더 eventId · eventType, `correlationId` = 키), DLT 관리자 재처리는 리스너를 직접 부르므로 `KafkaListenerDeadLetterReplayer`가 같은 값을 따로 연다. 아웃박스 릴레이는 메시지의 eventId · eventType · `correlationId`(= 메시지 키), 주문 스케줄러(`OrderScheduler`)는 `correlationId`(= 대상 주문 ID)만 넣는다

## 7. 주문 조회

- 주문 조회(#742)는 `app.order.OrderQueryService`가 상세 · 목록 · 타임라인 · 관리자 목록/이력을 읽기 전용으로 제공한다. 서비스 사이 전용 판매자 미종결 주문상품 수(#1120, `in/web/internal/SellerOrderItemController`, `GET /internal/sellers/{sellerId}/order-items/summary`, 인증 헤더 없음 · Gateway가 `/internal/**` 차단)는 공유 계약 `shared.order.out.SellerOrderItems`(응답 `shared.order.dto.SellerOrderItemSummary`, 다른 도메인의 동기 호출 계약)를 구현한 `OrderQueryService.summarize`가 '주문이 취소되지 않았고 주문상품이 ORDERED'인 건수를 주문 · 주문상품 조인 쿼리 한 번으로 센다(주문 전체 취소는 주문상품을 ORDERED로 남기므로 주문 상태로 거른다, 인덱스 `idx_order_item_seller_status`, `V202611101300`). 컨트롤러는 그 계약을 같은 모양으로 HTTP에 낸다(`sellerId`는 숫자). 주문은 개수만 주고 판매자 상태 · 탈퇴 판단은 부르는 쪽이 한다. 잘못된 판매자 ID(숫자 아님 · 1 미만)는 400 `INVALID_SELLER_ID`. 챗봇의 회원 최근 주문(#1191, `in/web/internal/MemberOrderController`, `GET /internal/members/{memberId}/orders?limit=`, 1~10 · 기본 5)도 같은 방식으로 공유 계약 `shared.order.out.MemberOrderHistory`(응답 `shared.order.dto.MemberOrderSummary`)를 `OrderQueryService.recent`가 구현한다: 구매자 목록과 같은 쿼리(주문 페이지 · 주문상품 · 배송 한 번씩)로 주문 · 주문상품 · 판매자별 배송의 상태(enum 이름) · 상품명 · 옵션 · 수량 · 택배사 코드 · 발송/배송 완료 시각만 준다. 배송지 · 연락처 · 송장번호 · 금액 · 자녀는 넣지 않는다(밖의 AI로 나간다). 생성 · 결제 · 취소 · 구매확정은 `OrderService`에 두며, 변경 응답 조립은 기존 쓰기 트랜잭션 안에서 조회 도우미를 재사용한다.
- 목록 상태 필터(#1280): 구매자 `GET /api/v1/orders` · 관리자 `GET /api/v1/admin/orders` · 판매자 `GET /api/v1/seller/orders`의 `status`(선택)는 응답 `status`와 같은 이름 · 같은 값 하나만 받는다(주문 `PENDING_PAYMENT` · `PAID` · `CANCELLED`, 판매자는 배송 `READY` · `SHIPPING` · `DELIVERED` · `CANCELLED`). 여러 값 · 범위 · 연산자는 두지 않고, 상태별 건수는 집계 API 없이 `totalElements`(`?status=X&size=1`)로 얻는다. 컨트롤러는 문자열로 받고 서비스가 enum 이름과 정확히 같을 때만 받아(소문자 · 공백 · 빈 값도 400, 멈춘 주문 `kind`와 같은 방식) 받는 값을 안내하는 400(`INVALID_ORDER_STATUS` · `INVALID_DELIVERY_STATUS`)을 낸다. 거르기 · 건수는 저장소 파생 쿼리(`…AndStatusOrderByIdDesc` · `countBy…AndStatus`, 큰 page 빈 페이지도 같은 조건)로 DB에서 한다. status가 없으면 기존 메서드를 그대로 부른다(`OrderQueryService.getOrders(memberId, status, …)` · `getAllOrders(status, …)`, `DeliveryService.getSellerOrders(memberId, status, …)` 오버로드). 인덱스는 기존 `idx_orders_member_id` · `idx_orders_status_payment_due_at` · `idx_delivery_seller_id`로 충분해 새 마이그레이션은 없다
- 관리자 목록 취소 시각(#1325): 주문 표에 취소 시각이 없어 상태 이력(`order_status_history`, 대상 ORDER · to_status 'CANCELLED')의 가장 최근 `occurred_at`을 쓴다. 주문 전체를 취소하는 모든 경로(공통 cancel: 결제 실패 · 관리자 결제 반영 취소 · 재고 부족 · 결제 마감 만료 · 판매 불가 판매자(결제대기), 구매자 취소, 회원 탈퇴, 판매자 전량 취소)가 이 이력을 남긴다 — 새 취소 경로도 남겨야 한다(#442 이전 취소 주문은 이력이 없어 null). 목록은 페이지의 취소 주문 ID만 모아 이력을 한 번(`findOrderCancelledAt`, group by) 읽어 붙인다. `cancelledFrom`(엄격 파싱 `uuuu-MM-dd'T'HH:mm:ss`, 틀리면 `INVALID_CANCELLED_FROM`)은 `o.status = CANCELLED and exists(이력 occurred_at >= from)`(`JpaOrderRepository.CANCELLED_SINCE`, count 같은 조건)로 거르고, status가 CANCELLED가 아니면 조회 없이 0건. 인덱스는 바깥 `idx_orders_status_payment_due_at` · 이력 `idx_order_status_history_order`로 충분해 새 마이그레이션 없음. 관리자 주문 상세 API는 두지 않는다(#1325-1 결정: 목록만, 취소 시각은 목록 · 이력 API로 본다)
  - 취소 건수 조회는 누적 취소 주문을 훑는다. 데이터가 커지면 `order_status_history(occurred_at) WHERE target_type='ORDER' AND to_status='CANCELLED'` 부분 인덱스를 검토한다
