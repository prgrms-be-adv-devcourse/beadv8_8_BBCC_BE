# 서버 처리 한계 측정 (#1471)

Gateway 전체 요청 수 제한(#1417, #1421)의 값을 정하려면 백엔드가 SLO를 지키며 버티는 처리량을 먼저 알아야 한다. 이 시나리오는 구매자 화면이 실제로 보내는 요청 묶음을 정해진 속도로 보내고, 속도를 단계별로 올려 SLO를 처음 넘는 지점을 찾는다.

- SLO: 측정 구간의 모든 요청 p95 500ms 이하, 오류율 1% 미만, 정한 속도로 화면을 모두 열었을 것(`dropped_iterations` 0)
- 이 폴더는 Gradle 소스 세트 밖이라 빌드 · 테스트에 들어가지 않는다. CI에서 돌리지 않는다

## 파일

| 파일 | 내용 |
|---|---|
| `capacity.js` | 속도 하나(`RATE`, 화면/초)로 예열 30초 + 측정 3분. 준비(회원 · 토큰 · 상품 · 예치금)와 정리(측정 주문 취소), 결과 한 줄 |
| `lib/screens.js` | 화면별 요청 묶음과 화면 비중 |
| `run.sh` | `RATES`를 낮은 값부터 하나씩 실행하고 SLO를 처음 넘은 단계에서 멈춘다. 결과는 `results/<RUN_ID>/` (git 제외) |

## 화면과 요청

FE develop의 화면 · 쿼리 코드를 따랐다. 같이 나가는 요청은 `http.batch`로 같이, 앞 응답을 기다리는 요청은 그 뒤에 보낸다.

| 화면 | 비중 | 요청 | 비로그인 |
|---|---:|---|:---:|
| 새 방문(홈) | 10 | `/members/me` → 상품 목록 2번 · 카테고리 · 자녀 · 안 읽은 알림 수 → 목록 상품의 찜 여부 | 가능 |
| 목록 쪽 넘김 · 정렬 | 15 | 상품 목록 → 찜 여부 | 가능 |
| 카테고리 목록 | 15 | 카테고리로 거른 목록 → 찜 여부 | 가능 |
| 상품 상세 | 28 | 상세 · 찜 수 · 찜 여부 · 자녀 · 조회 기록 → 리뷰 요약 · 리뷰 | 가능 |
| 장바구니 담기 | 6 | 담기 → 장바구니 | |
| 장바구니(주문서) | 8 | 장바구니 · 배송지 · 잔액 · 자녀. 6줄 이상이면 한 줄 빼기 → 장바구니 | |
| 찜 누르기 · 풀기 | 5 | 찜 · 찜 취소 → 찜 수 · 찜 여부 | |
| 주문 내역 | 5 | 주문 목록 · 상태별 건수 4개 | |
| 마이페이지 | 4 | 자녀 · 배송지 · 잔액 · 결제 내역 · 조르기 · 상태별 건수 4개 | |
| 알림 | 2 | 알림 목록 | |
| 주문하기 | 2 | 주문서 요청 → 주문(예치금) → 결제가 끝날 때까지 1초마다 주문 조회(최대 10번) → 타임라인 · 결제 | |

- 비중은 가정이다. 기획서에 사용자 행동 수치가 없어서 목록 → 상세 → 장바구니 → 주문으로 줄어드는 이커머스 깔때기를 가정했다. 실제 사용 데이터가 생기면 `lib/screens.js`의 `SCREENS`를 고친다
- 비로그인으로 열 수 있는 화면은 `ANON_RATIO`(기본 0.3)만큼 토큰 없이 연다
- 화면 하나에 요청은 평균 4.3개다(가짜 서버로 잰 값). 결과의 `rps`가 실제 요청 수다

## 준비

1. 대상은 dev 서버다(`https://dev-api.kidly.kro.kr`). 개발용 API(`/dev/members` · `/dev/tokens` · `/dev/wallets/me/charges`)가 있는 local · dev 프로필에서만 돈다
2. 공유 서버라 팀 채널에 시간을 알린다. 측정 중에는 다른 사람의 요청도 느려진다
3. 관리자 화면 「요청 수 제한」에서 제한을 끈다. 켜 두면 측정이 서버가 아니라 제한 값을 잰다. 끝나면 다시 켠다
4. k6를 설치한다(`brew install k6`, 1.0 이상). Docker로 돌리지 않는다. 가짜 서버로 확인할 때 Docker Desktop의 호스트 연결이 화면 5개/초에서도 연결 시간 초과를 냈다. 로컬 k6는 같은 조건에서 0건이었다
5. 서버 지표를 같이 보려면 [부하 테스트 모니터링](../../../deploy/monitoring/docs/load-test-monitoring.md)의 SSH 터널을 연다

## 실행

```bash
cd apps/gateway/load-test
BASE_URL=https://dev-api.kidly.kro.kr \
K6_PROMETHEUS_RW_SERVER_URL=http://localhost:9090/api/v1/write \
K6_PROMETHEUS_RW_TREND_STATS='p(95),p(99),avg,max' \
./run.sh
```

| 환경 변수 | 기본값 | 뜻 |
|---|---|---|
| `BASE_URL` | (필수) | Gateway 주소 |
| `RATES` | `5 10 20 30 40 60 80` | 단계별 화면/초. 앞 단계가 SLO를 넘으면 뒤는 돌리지 않는다 |
| `DURATION` · `WARMUP` | `3m` · `30s` | 단계마다 측정 · 예열 시간(`s` · `m`) |
| `COOLDOWN` | `60` | 단계 사이 쉬는 초. Kafka 처리 · GC가 가라앉게 한다 |
| `USERS` | `100` | 더미 회원 수 |
| `ANON_RATIO` | `0.3` | 비로그인으로 여는 비율 |
| `ORDERS` | `on` | `off`면 주문하기를 빼고 예치금도 채우지 않는다 |
| `MAX_VUS` | 화면/초 × 20 | 동시에 열려 있을 수 있는 화면 수 상한 |
| `RUN_ID` | 날짜-시각 | 결과 폴더와 Grafana `testid` 앞부분 |

속도 하나만 돌리려면 `RATE=20 BASE_URL=... k6 run capacity.js`.

## 결과 읽기

단계마다 `results/<RUN_ID>/steps.jsonl`에 한 줄이 쌓인다.

```json
{"rate":30,"rps":128,"p95":54,"failed":0,"dropped":0,"slo":true}
```

- `rate`는 화면/초, `rps`는 측정 구간의 초당 요청 수, `p95`는 ms, `failed`는 오류율, `dropped`는 정한 속도로 열지 못한 화면 수다
- 처리 한계 μ는 `slo`가 `true`인 마지막 단계의 `rps`다. 꺾인 단계와 그 앞 단계 사이를 더 잘게 나눠(`RATES="40 45 50"`) 다시 재면 정확해진다
- `dropped`가 0보다 크면 서버가 느려져 열린 화면이 쌓인 것이다. 부하 발생기 PC의 CPU가 100%였다면 측정이 무효다
- 어느 서비스가 먼저 막혔는지는 Grafana 「Kidly 부하 테스트」에서 같은 시간의 Pod CPU · 메모리 · DB 커넥션을 본다
- 응답 시간에는 PC에서 dev까지의 네트워크 시간이 들어 있다

## 만드는 데이터와 정리

| 데이터 | 정리 |
|---|---|
| 더미 회원 `load-capacity-1` ~ `load-capacity-<USERS>` | key가 같으면 같은 회원이라 다시 돌려도 늘지 않는다 |
| 예치금 개발용 충전(원장 `DEV_CHARGE`) | 잔액이 30만 원 미만인 회원만 100만 원 |
| 장바구니 · 찜 · 상품 조회 기록 | 남는다. 장바구니는 5줄 근처로 유지된다 |
| 주문 | 실행이 끝날 때 측정 회원의 결제 대기 · 결제 완료 주문을 모두 취소한다(재고 · 예치금이 돌아온다) |

주문은 재고가 넉넉한(`AVAILABLE`) 옵션에만 1개씩 넣는다. 그래도 dev 상품의 재고는 측정 중에 잠깐 줄어든다.

## 한계

- 화면 비중이 가정이므로 μ도 이 비중에서의 값이다. 비중이 크게 바뀌면 다시 잰다
- TanStack Query 캐시(60초)로 FE가 다시 부르지 않는 요청까지 보내므로 실제보다 조금 무거운 쪽이다
- 비로그인 요청은 모두 부하 발생기 IP 하나에서 나간다. 요청 수 제한을 끄고 재는 이유 중 하나다
- 토큰은 30분 동안 쓸 수 있다. 단계 하나(준비 + 예열 + 측정 + 정리)가 30분 안에 끝나야 한다
