# 사용자 유형별 더미 데이터 (#1289)

구매자 · 판매자 · 자녀 · 상품과 찜 · 장바구니 · 주문 · 구매확정 · 리뷰를 Gateway API로만 넣는다. SQL로 넣지 않으므로 Kafka 이벤트가 그대로 나가 도메인마다의 복사본 · 지갑 · 검색 색인이 함께 맞는다.

- Node 24 내장 `fetch`만 쓴다. `npm install`이 필요 없다
- 이 폴더는 Gradle 밖이라 빌드 · 테스트에 들어가지 않는다
- 같은 명령을 다시 돌리면 이어서 넣는다. 다 넣은 뒤 다시 돌리면 아무것도 바꾸지 않는다

## 파일

| 파일 | 내용 |
|---|---|
| `seed.mjs` | 실행 진입점. 인자 확인, dev 확인, 단계 실행, 진행 줄 출력 |
| `verify.mjs` | 기록의 행이 API로 보이는지 읽기만 해서 확인한다 |
| `lib/plan.mjs` | 규모별 개수와, 번호마다 늘 같은 값을 내는 더미 값(고정 난수) |
| `lib/phases.mjs` | 단계별 요청 |
| `lib/api.mjs` | Gateway 요청, 재시도, 토큰 |
| `lib/manifest.mjs` | 만든 ID 기록 읽기 · 쓰기 |

## 규모

| | `small` | `medium` |
|---|---|---|
| 구매자 | 10 | 1,000 |
| 판매자 | 3 | 50 |
| 자녀 | 20 | 2,000 (구매자마다 0~4명, 평균 2명) |
| 배송지 | 10 | 1,000 (구매자마다 기본 배송지 1개) |
| 상품 | 20 | 5,000 (판매자마다 고르게, 옵션 2~6개, 옵션마다 재고 999) |
| 찜 | 40 | 30,000 |
| 장바구니 줄 | 20 | 3,000 |
| 주문 | 30 | 12,000 (주문상품 15,554) |
| 구매확정 주문 | 26 | 8,959 (주문상품 11,615) |
| 리뷰 | 16 | 6,934 |

주문은 모든 단계가 화면에 보이도록 일부만 끝까지 진행한다. 결제완료에서 멈춤 8%, 발송 8%, 배송완료 9%, 구매확정 75%. 구매확정한 주문상품의 60%에 리뷰를 쓴다. 주문의 절반쯤은 자녀를 고른다. 인기 상품일수록 찜 · 주문이 몰리도록 앞 번호 상품을 더 자주 고른다.

값은 번호마다 고정 난수로 정한다. 같은 규모면 몇 번을 돌려도 같은 이름 · 가격 · 주문 구성이 나온다.

## 준비

로컬은 아래가 모두 떠 있어야 한다(README 루트의 로컬 실행 참고).

- `docker compose up -d` (PostgreSQL · Kafka)
- Gateway(8083), 회원(8081), 상품(8089), 주문(8091), 결제(8087), 커뮤니티(8092)
- 정산 · 알림 · 추천 · 검색은 없어도 넣을 수 있다. 다만 검색 서비스가 꺼져 있으면 상품 목록(`GET /api/v1/products`) 색인은 나중에 채워진다

회원 서비스는 더미 회원 · 보호자 본인인증 개발용 API(`POST /api/v1/dev/members`, `POST /api/v1/dev/guardian-verifications`)가 있는 버전이어야 한다. 개발용 API는 local · test · dev 프로필에서만 열린다.

## 실행

저장소 루트에서 실행한다.

```bash
node tools/seed-data/seed.mjs --env local --scale small        # 먼저 작게 확인
node tools/seed-data/verify.mjs --env local                    # API로 확인
node tools/seed-data/seed.mjs --env local --scale medium       # 목표 규모
node tools/seed-data/seed.mjs --env local --scale small --only orders   # 한 단계만
```

| 인자 | 기본값 | 뜻 |
|---|---|---|
| `--env` | 없음(필수) | `local` 또는 `dev` |
| `--scale` | 없음(필수) | `small` 또는 `medium` |
| `--only` | 없음 | 이 단계만 돌린다. 앞 단계가 기록에 있어야 한다 |
| `--concurrency` | `8` | 동시에 보내는 작업 수(1~64) |

| 환경 변수 | local 기본값 | 뜻 |
|---|---|---|
| `SEED_BASE_URL` | `http://localhost:8083` | Gateway 주소 |
| `SEED_ADMIN_EMAIL` | `admin@kidly.local` | 판매자 신청을 승인할 관리자 |
| `SEED_ADMIN_PASSWORD` | `local-admin-password` | 위 관리자의 비밀번호 |

### dev

dev는 실제 운영 서버다. `--yes-i-know-dev-is-production`을 붙이고 환경 변수 세 개를 모두 줘야 돈다. 하나라도 빠지면 요청을 보내기 전에 멈춘다. 관리자 비밀번호는 셸 기록에 남지 않게 넣는다.

```bash
read -rs SEED_ADMIN_PASSWORD && export SEED_ADMIN_PASSWORD
SEED_BASE_URL=https://<dev Gateway> SEED_ADMIN_EMAIL=<관리자 이메일> \
  node tools/seed-data/seed.mjs --env dev --scale small --yes-i-know-dev-is-production
```

## 단계

앞 단계가 기록한 ID를 뒤 단계가 쓴다. 한 단계가 실패하면 거기서 멈추고 기록을 저장한다. 원인을 고친 뒤 같은 명령으로 이어서 돌린다.

| 단계 | 요청 | 다시 돌릴 때 |
|---|---|---|
| `members` | `POST /api/v1/dev/members` (구매자 · 판매자) | 같은 key면 같은 회원을 돌려준다 |
| `sellers` | 판매자 신청 → 관리자 승인 | 최근 신청을 읽고 없으면 신청, 심사 중이면 승인 |
| `addresses` | 기본 배송지 등록 | 배송지가 있으면 그것을 쓴다 |
| `children` | `POST /api/v1/dev/guardian-verifications` → 자녀 등록 | 자녀 목록에서 이름으로 찾고 없는 자녀만 등록 |
| `products` | 상품 등록 → 판매 시작 | 판매자 상품 목록에서 이름으로 찾는다(이름 끝의 `KD-번호`) |
| `wallets` | 개발용 예치금 충전 | 잔액을 읽고, 아직 넣지 않은 주문 금액보다 모자란 만큼만 충전 |
| `favorites` | `PUT /api/v1/favorites/{productId}` | 같은 요청은 그대로 204 |
| `orders` | 주문 → 결제완료까지 기다림 | 주문마다 고정 `Idempotency-Key`라 같은 주문을 돌려준다 |
| `fulfillment` | 발송 → 배송완료 → 구매확정 | 배송 상태를 읽고 남은 단계만 |
| `reviews` | `POST /api/v1/reviews` | 409(이미 씀)면 내 리뷰에서 ID를 찾는다 |
| `carts` | `POST /api/v1/cart/items` | 장바구니를 읽고 없는 줄만 담는다 |

- 장바구니는 주문 뒤에 담는다. 결제된 주문과 같은 (옵션, 자녀) 칸은 주문 도메인이 장바구니에서 빼기 때문이다(#641)
- 복사본은 Kafka로 늦게 생긴다. 찜 · 장바구니 · 주문의 404(상품 · 자녀 복사본 없음)와 리뷰의 403(작성 자격 없음)은 최대 2분쯤 기다리며 다시 보낸다
- 5xx · 429 · 네트워크 오류는 물러났다가 다시 보낸다. 그 밖의 4xx는 바로 멈춘다
- 진행 줄은 단계마다 한 줄이다: 대상 수 · 처리 수 · 기록에 있어 건너뛴 수 · 보낸 요청 수 · 걸린 시간. 토큰 · 요청 본문 · 개인정보는 출력하지 않는다

## 기록(manifest)

`tools/seed-data/.manifest/{env}.json`에 만든 ID를 남긴다. git에 올리지 않는다(`.gitignore`). 다시 돌릴 때 끝난 것을 건너뛰고, 나중에 정리할 대상을 정확히 고르는 데 쓴다. 다른 `--scale`이나 다른 주소로 만든 기록이면 멈춘다.

| 키 | 값 |
|---|---|
| `members` | 시드 key(`buyer-0001` · `seller-001`) → 회원 ID |
| `sellerApplications` | 판매자 key → 승인된 신청 ID |
| `addresses` | 구매자 key → 배송지 ID |
| `guardians` | 보호자 본인인증을 만든 구매자 key |
| `children` | 구매자 key → 자녀 ID 목록 |
| `products` | `product-00001` → 상품 ID · 판매자 key · 옵션 ID와 가격 |
| `wallets` | 구매자 key → 이 스크립트가 충전한 금액 합 |
| `favorites` | 구매자 key → 찜한 상품 ID |
| `orders` | `order-000001` → 주문 ID · 주문상품 ID · 판매자 주문(배송) ID · 지금 단계 |
| `reviews` | 주문상품 ID → 리뷰 ID |
| `cartItems` | 구매자 key → 장바구니 줄 ID |

기록을 잃어도 다시 돌리면 서버에서 찾아 같은 ID로 다시 채운다. 예외는 충전이다. 기록이 없으면 이미 결제된 주문인지 알 수 없어 그 금액만큼 한 번 더 충전한다(주문은 다시 생기지 않고 잔액만 늘어난다).

## dev에서 시드 데이터 알아보기

| 대상 | 표시 |
|---|---|
| 회원 | `member.member.registration_key`가 `seed-bulk:`로 시작(`seed-bulk:buyer-0001`). 이메일은 비어 있어 환영 메일이 나가지 않는다 |
| 닉네임 | `시드구매자0001` · `시드판매자001` |
| 보호자 본인인증 | `childprofile.guardian_verification.identity_key`가 `seed-bulk:`로 시작. 이름 `더미 보호자` |
| 판매자 | 사업자등록번호가 `9`로 시작하는 10자리(`9000000001`) |
| 상품 | 이름 끝이 `(KD-00001)`, 옵션 SKU 코드가 `SEED-product-00001-1` |
| 배송지 | 연락처 `010-0000-0001` 꼴 |
| 송장 | 택배사 `DUMMY`, 송장 번호 `SEED{판매자 주문 ID}` |

## 정리

정리는 아직 자동화하지 않았다. 지울 때는 기록의 ID(또는 위 표시)로 아래를 도메인마다 지워야 한다. 다른 도메인의 복사본은 Kafka 이벤트로만 맞춰지므로 SQL로 한쪽만 지우면 어긋난다. 회원 탈퇴 · 상품 판매 중지 같은 API를 쓰거나, 도메인마다 같이 지우는 절차를 따로 만든다.

| 도메인 | 지울 것 |
|---|---|
| 회원 | 시드 회원, 배송지 |
| 판매자 | 판매자 신청 · 판매자 |
| 자녀 프로필 | 보호자 본인인증, 자녀 프로필 · 성장 이력 |
| 상품 | 시드 상품 · 옵션 · 재고 · 실측, 판매자 복사본 |
| 주문 | 주문 · 주문상품 · 판매자 주문(배송) · 타임라인, 장바구니 줄, 회원 · 자녀 · 상품 복사본 |
| 결제 | 지갑 · 원장 · 개발용 충전 · 결제 · 결제 이벤트 기록 |
| 정산 | 구매확정으로 생긴 정산 대상 |
| 커뮤니티 | 찜 · 찜 수, 리뷰 · 리뷰 집계 · 작성 자격, 상품 복사본 |
| 추천 · 검색 · 알림 | 상품 · 판매자 · 자녀 복사본, 검색 색인, 주문 · 배송으로 생긴 알림함 항목 |

## 걸린 시간

로컬(Mac, 서비스 한 대씩, 동시 8)에서 `small` 첫 실행이 19초(요청 578)였다. 그중 주문이 13초로, 결제가 Kafka를 거쳐 끝나기를 주문마다 3초쯤 기다린다. 다 넣은 뒤 다시 돌리면 0.1초에 요청 0이다.

`medium`은 아직 돌리지 않았다. `small`의 단계별 처리 속도에서 늘린 추정은 주문 약 85분(동시 8), 상품 약 5분, 찜 약 3분(복사본 지연 없이 초당 200건), 나머지 합 약 5분이다. 주문은 결제를 기다리는 시간이 대부분이라 `--concurrency 32`면 결제 서비스가 따라오는 한 20분 남짓으로 줄 것으로 본다.
